## Engine et compatibilité de bout en bout

Admin épingle `vendor/novlearn-exercise-engine-0.1.0.tgz`, SHA256 **`d4d3abc408ab37f2f8a5faa512964b48947828bae9209cb1460b47111ca582f9`**, Cortex `0.151.0`, schéma 5, contrat `schema-5;engine-0.1.0`, génération `mulberry32-rejection-v1`, canonisation `pg-jsonb-text-v1`. Archive, intégrité du lockfile et fichier installé contrôlés avec succès. Le vérificateur ne contrôle qu'un fichier installé en plus de l'archive : ce n'est pas une comparaison exhaustive de `node_modules`.

Appels Admin observés : `validateDefinition`, `instantiateExercise`, `projectPublicInstance`, `gradeAnswer`. Génération, contraintes, instanciation et correction restent dans Engine. L'Admin construit des formulaires canoniques, filtre les sorties privées et compare des empreintes ; aucune réimplémentation algébrique concurrente identifiée dans ce parcours. Le transport local JSON protocole 1 adapte l'exécution, pas les mathématiques. L'adaptateur historique est isolé dans Engine (`adapters/legacy`), pas utilisé pour convertir implicitement les sauvegardes Admin.

Le dépôt Engine annonce **package 0.2.0**, avec `sampleDisplayGraph`, tout en conservant **schéma 5/pipeline 0.1.0** dans les contrats. Ce n'est pas à lui seul une rupture de correction ; c'est une identité de distribution différente. `engine-graphs.md` conserve les échecs de certification : signature Windows refusée, dépassements historiques, collecte Linux `EAGAIN` sous 64 processus. Le smoke du package Linux passe historiquement avec un maximum de 4 828,772 ms, marge faible. Ne pas adopter automatiquement cette archive.

**Incompatibilité actuelle démontrée côté NovLearn :** `frontend/app/components/Exercise/ExerciseLoader.tsx` lit `exercises.content`, appelle `utils/variableGenerator.ts` et envoie un verdict client `is_correct`. `ExerciseRenderer.tsx` attend l'ancien format `element.content`. `backend/routers/ds.py` reçoit aussi `body.is_correct`. `duel-server/src/rooms/DuelRoom.ts` traite `msg.isCorrect` et prépare un attendu historique. Aucun package Engine n'est déclaré dans les manifestes frontend/duel inspectés. Une révision Admin canonique dans `exercise_versions` n'est donc pas consommable telle quelle par ces parcours. Les nouveaux parents ont `content = {}` : un lecteur historique peut obtenir un exercice vide. Une simple correspondance de numéros de version ne résout pas cet écart.

## Sécurité observée, sans exploitation

Protections Admin réelles : contrôles serveur par opération, origine POST exacte, JSON lu et borné à 256 Kio, cookies HttpOnly/SameSite/Secure en HTTPS, réponses privées sans cache ; session Staging fixée au projet prévu, aucun client privilégié dans ce parcours. `ADMIN_STAGING_SECURITY_REVIEW` est un marqueur non vide de configuration, **pas une attestation vérifiée automatiquement**. Les valeurs de secrets et bundles clients n'ont pas été inspectés : absence de fuite exhaustive non certifiée.

Sur **Staging relu** : RLS active sur profils, exercices, versions et tentatives. Les policies restrictives protègent profils et brouillons canoniques ; le trigger de rôle interdit l'auto-attribution et les changements d'identité. La sauvegarde RPC relue est invoker, contrôle Admin, verrouille les lignes et contrôle l'empreinte. Ne pas conclure à une fuite des nouveaux brouillons sur la seule présence d'une policy permissive : les restrictives s'appliquent aussi.

**Écarts prioritaires :**

1. `get_random_exercise` est `SECURITY DEFINER`, appelable anon selon advisors, sans contrôle d'identité ni filtre canonique/publication dans son corps relu ; il retourne `row_to_json(e)`. Il contourne les protections RLS selon les privilèges du propriétaire et expose une surface de lecture complète, y compris les parents canoniques. Aucune ligne retournée ni exploitation testée.
2. Les lectures directes de `exercises` autorisent encore les lignes historiques (`catalog_id IS NULL`) avec `content`. Les réponses historiques peuvent donc rester accessibles. Fermer ces accès exige d'abord un consommateur serveur fonctionnel.
3. Les tentatives canoniques sont protégées par trigger contre les écritures client versionnées, mais les tentatives sans version restent acceptables selon les anciennes règles. Le front/duel conserve ses verdicts clients. L'ownership des policies relues n'est pas neutralisé par « No guest access », qui est bien **restrictive** aujourd'hui.
4. Grants de table très larges encore présents sur des tables historiques, dont `TRUNCATE` pour anon/authenticated. RLS ne protège pas TRUNCATE ; cela ne démontre pas une route HTTP permettant de l'exécuter. Revoir les privilèges effectifs et RPC sur copie, sans test destructeur distant.
5. Advisors Staging : **0 erreur, 31 avertissements, 7 informations**, dont 30 alertes de fonctions definer et protection des mots de passe divulgués désactivée. Une fonction definer avec garde interne n'est pas automatiquement exploitable ; examiner corps/ACL individuellement. [Advisors officiels](https://supabase.com/docs/guides/database/database-linter), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [sécurité des mots de passe](https://supabase.com/docs/guides/auth/password-security).

MFA/AAL2 non imposé dans l'autorisation Admin inspectée. Révocation, récupération, limitations de connexion et exploitation doivent être reçues sur la cible. Ne pas annoncer les vulnérabilités npm historiques corrigées ou toujours présentes sans nouvel audit dédié.

## Exécution : ce qui bloque réellement

Le runtime installé exige **Linux x64, Python >=3.11 à `/usr/bin/python3`, cgroup v2 déjà borné, mémoire <=384 Mio, swap 0, pids <=64**, accès aux compteurs cgroup, `fork`, `prctl/seccomp`. Heap worker 128 Mio, 5 s **file comprise**, entrée 1 Mio, sortie 2 Mio, stderr 64 Kio ; Admin limite le host à 1 opération active/4 en attente. Refus fermé si les protections manquent (`dist/node-host/linux/job.py`, `executor.js`). Les blocages Windows documentés concernent Code Integrity et le lanceur natif ; ils ne prouvent pas une erreur mathématique.

Vercel Node offre les API Node et Node 24.x : aucune preuve officielle consultée d'une interdiction générale des processus enfants ou d'Engine. Les fonctions ont toutefois un cycle de vie distribué et aucune garantie documentée consultée du profil cgroup/seccomp/Python exigé. **Incompatibilité de profil non qualifié**, pas impossibilité universelle. Le code ajoute en outre un refus Vercel volontaire. Le transport existant n'est pas un client de service distant de production.

Les snapshots privés et les limites de travaux sont **en mémoire de processus** : expiration 10 min, 2 snapshots/Admin, 32 au total, 512 Kio chacun ; 1 travail/Admin et 2 globalement. Vercel ou plusieurs réplicas peuvent perdre un aperçu ou multiplier les quotas. Externaliser seulement le calcul ne corrige pas cela. La correction refuse alors 410, elle ne doit jamais recréer implicitement l'instance.

## Choix d'architecture proposé

**Recommandation : un hôte Linux géré, Next.js standalone et un worker Engine séparé dans un périmètre de ressources sur le même hôte.** Un seul processus Admin pour le pilote conserve les snapshots actuels ; le worker garde le profil certifié sans réseau ni secrets. Réutiliser le protocole privé existant, adapter seulement le lancement local au profil d'exploitation approuvé. Une bibliothèque mathématique commune, un déploiement coordonné ; pas de nouvelle API mathématique publique ni de nouveau backend FastAPI Admin.

| Option | Simplicité et isolation | Délais, quotas et exploitation | Coût et compatibilité |
| --- | --- | --- | --- |
| Engine dans le serveur Linux, host natif direct | Moins de transport ; code `runEngine` déjà présent | Le cgroup est partagé avec Next : son plafond inclut le serveur. OOM peut emporter l'UI ; le requalifier sous 384 Mio, sans augmenter le quota | Un hôte ; compatible standalone. Variante possible si la qualification démontre une marge suffisante |
| Même hôte, worker borné séparé — recommandé | Un hôte à administrer, isolation des pannes/mémoire ; réutilise le travail local | Proxy HTTPS pour Admin, liaison privée worker, supervision et mises à jour ; mémoire Next distincte du quota Engine | Facturation d'hôte et sauvegardes, y compris au repos ; devis selon région/capacité, aucun tarif inventé |
| Admin Vercel + service Linux Engine | Conserve la cible D13 ; ajoute TLS, authentification de service, rotation et supervision | Aller-retour réseau ; 5 s natives conservées, transport local 10 s à respecter/requalifier. Résoudre snapshots et quotas distribués avant réception | Deux factures, trafic et ressources Vercel ; pertinent si Vercel est maintenu comme contrainte ferme |
| Engine natif dans Vercel Functions | Transport minimal | Qualification cgroup/Python/seccomp et snapshots non démontrée ; ne pas retirer le refus actuel pour essayer en production | Pas retenu pour le chemin critique ; étude isolée éventuelle, sans réduire les protections |

Sources officielles consultées le 21/10/2026 : [Vercel Node](https://vercel.com/docs/functions/runtimes/node-js), [versions](https://vercel.com/docs/functions/runtimes/node-js/node-js-versions), [limites](https://vercel.com/docs/functions/limitations), [tarification](https://vercel.com/docs/functions/usage-and-pricing), [Next.js auto-hébergé](https://nextjs.org/docs/app/guides/self-hosting), [quotas Docker](https://docs.docker.com/engine/containers/resource_constraints/). Vercel documente 250 Mo de bundle standard, 4,5 Mo par requête/réponse, 2 Go Hobby/4 Go Pro, durée Fluid 300 s Hobby et 800 s Pro standard ; ces plafonds ne remplacent pas nos bornes. Node est choisi par version majeure et ses correctifs évoluent : requalification nécessaire. Coût Fluid : CPU actif, mémoire allouée et invocations ; le budget final dépend du plan et de la charge mesurée. Les options beta ne sont pas retenues comme dépendances V1.

Le futur mobile consommera une API applicative authentifiée de création/reprise d'instance et soumission de réponse. Engine fournit contrats et verdicts ; les serveurs conservent les snapshots privés. Aucune exigence d'embarquer Cortex ou le host Linux dans le mobile, ni de figer aujourd'hui un microservice universel.
